# 1. Auth & Tokens

## #A-001 🔴 [Auth] PKCE `plain`-Methode akzeptiert + Vergleich nicht constant-time
**Datei:** [src/auth/pkce.ts:7-14](src/auth/pkce.ts:7), [src/routes/auth.ts:80](src/routes/auth.ts:80)
**Beschreibung:** `code_challenge_method` darf `"plain"` sein. Bei `plain` wird `verifier === challenge` ohne timing-safen Vergleich gemacht. OAuth 2.1 (RFC 9700) verlangt S256 für public Clients.
**Impact:** Authorization-Code-Interception kann den Verifier in Plain rekonstruieren; zusätzlich Timing-Side-Channel via String-Equality.
**Fix:** `code_challenge_method` Schema auf `z.literal("S256")` reduzieren. Plain-Pfad in `verifyPkce` entfernen oder via Tenant-Feature-Flag deaktivieren. Ohnehin ist constantTimeEqual auf den verifier statt strict equality.

## #A-002 🔴 [Auth] HMAC-Signatur signiert nur Pathname, nicht Query-String
**Datei:** [src/middleware/auth.ts:69-77](src/middleware/auth.ts:69)
**Beschreibung:** `signingString = METHOD\n${url.pathname}\n${timestamp}\n${bodyHash}` — `url.search` (Query-String) ist nicht enthalten.
**Reproduktion:** Tenant signiert `GET /v1/orders?limit=10`. Ein MITM/Replay kann Query auf `?limit=10000&customer_id=cust_OPFER` ändern; HMAC bleibt gültig.
**Impact:** Authentifizierte GET-Liste-Requests sind tamper-bar (limit-Erhöhung → DoS, customer_id-Filter → IDOR-Light über Listen).
**Fix:** `${url.pathname}${url.search}` ins Signing einbeziehen, beidseitig (Server + SDK). Bestehende Clients per Versionsbump invalidieren.

## #A-003 🟠 [Auth] JWT verifiziert keinen `iss`-Claim
**Datei:** [src/auth/jwt.ts:76-79](src/auth/jwt.ts:76)
**Beschreibung:** `verifyJwt` checkt `aud`, `tenant_id`, `exp`, Signatur, `alg=HS256` — aber nicht `iss`. Issuer wird in `signJwt` (`tenants:<id>`) gesetzt, aber bei verify nicht gegen ein Pin geprüft.
**Impact:** Wenn der gleiche per-Tenant-Secret jemals für anderen Issuer verwendet würde (z.B. interne Tools), kann ein Token von dort als Customer-JWT akzeptiert werden.
**Fix:** Im `verifyJwt` `payload.iss === \`tenants:${expectedTenantId}\`` erzwingen.

## #A-004 🟠 [Auth] JWT keine Clock-Skew-Toleranz, keine `nbf`/`iat`-Prüfung
**Datei:** [src/auth/jwt.ts:78-79](src/auth/jwt.ts:78)
**Beschreibung:** `if (payload.exp < now)` ohne Toleranzfenster. `nbf`/`iat` werden ignoriert.
**Impact:** Bei minimal abweichender Worker-vs-Client-Uhr (CF-Edge Clocks driften) bekommen frische Token „expired"-Antworten. Fehlende `iat`/`nbf` lassen weit-in-Zukunft datierte Token akzeptieren (keine Hard-Begrenzung neben `exp`).
**Fix:** ±60s Skew-Toleranz auf `exp`. `if (payload.iat > now + 60)` als „token from future"-Reject. `nbf` verifizieren falls vorhanden.

## #A-005 🟠 [Auth] Kein `kid`-Claim → JWT-Key-Rotation invalidiert alle Tokens
**Datei:** [src/auth/jwt.ts:43-50](src/auth/jwt.ts:43), [src/services/rotation.ts:46-61](src/services/rotation.ts:46)
**Beschreibung:** JWT-Header enthält nur `alg/typ`, kein `kid`. Beim `rotateTenantJwtSecret` wird das alte Secret in `customer_jwt_secret_previous` für 7d gehalten, aber `verifyJwt` verwendet immer nur das aktuelle Secret. Kein Doppel-Reader für JWT.
**Impact:** Bei Secret-Rotation werden ALLE outstanding Customer-JWTs sofort ungültig (15min `expires_in`, daher max. 15min Forced-Re-Login).
**Fix:** Entweder `kid` im Header + Verify versucht aktuelles Secret zuerst, dann previous; oder Sekret-Rotation auf 0-Down-Time-Pattern umstellen (Doppel-Reader wie bei API-Keys, siehe `auth.ts:80-83`).

## #A-006 🟠 [Auth] OAuth `authorization_code`-Verbrauch nicht atomisch
**Datei:** [src/routes/auth.ts:142-155](src/routes/auth.ts:142)
**Beschreibung:** Code-Exchange macht SELECT, prüft `consumed_at`, dann UPDATE `consumed_at`. Zwei parallele Requests mit gleichem Code sehen beide `consumed_at == null`, beide consumieren erfolgreich, beide bekommen verschiedene Token-Paare.
**Impact:** Single-Use-Garantie der OAuth-Spec verletzt; dupliziertes Token-Issuance.
**Fix:** Conditional Update via SQL `UPDATE auth_authorization_codes SET consumed_at=? WHERE code_hash=? AND consumed_at IS NULL` und Anzahl-betroffene-Zeilen prüfen (D1: `result.meta.changes === 1`). Bei 0 → reject.

## #A-007 🟠 [Auth] Refresh-Token-Replay-Detection: scope wird unverändert weitergegeben
**Datei:** [src/auth/refresh.ts:81-88](src/auth/refresh.ts:81)
**Beschreibung:** Beim Rotate wird `scope` 1:1 vom alten auf den neuen Refresh-Token übernommen. Wenn ein Customer in der Zwischenzeit Scopes verloren hat (z.B. revoke, blocked), bekommt er sie beim Refresh wieder.
**Impact:** Privilege-Persistence auch nach Scope-Reduktion. Niedrig in v1 (nur 1 Scope `customer_self`), aber bricht beim ersten weiteren Scope.
**Fix:** Customer-Status + Scope-Quelle zur Refresh-Zeit neu auflösen (DB-Lookup `customers.blocked`, evtl. `customer_scopes`-Tabelle).

## #A-008 🟠 [Auth] OAuth-Token-Endpoint produziert orphan Refresh-Tokens
**Datei:** [src/routes/auth.ts:158-169](src/routes/auth.ts:158), [src/auth/token-issuance.ts:38](src/auth/token-issuance.ts:38)
**Beschreibung:** Bei `grant_type=refresh_token` wird `rotateRefresh()` aufgerufen, dann `issueTokenPair()` welches intern noch einen weiteren `issueRefresh()` macht (Zeile 38). Im Response wird aber `result.new_refresh.plain` von rotateRefresh zurückgegeben. Der zweite Refresh-Token bleibt orphan in der DB.
**Impact:** DB-Wachstum + verwirrter Audit-Trail; kein direkter Sicherheitsbug, aber ein potenziell gültiger Refresh-Token wird ungenutzt.
**Fix:** `issueTokenPair` so refactorn dass es kein Refresh erzeugt wenn bereits einer zur Verfügung steht; oder spezialisierte `issueAccessOnly()`-Funktion einführen.

## #A-009 🔴 [Auth] Refresh-Token-Rotation Race auf `rotated_at`
**Datei:** [src/auth/refresh.ts:64-79](src/auth/refresh.ts:64)
**Beschreibung:** SELECT, Check `rotated_at`, dann UPDATE `rotated_at`. Race: zwei parallele Refresh-Aufrufe mit gleichem Token sehen beide `rotated_at == null`, beide rotieren successfully, beide bekommen ein neues Token-Paar.
**Reproduktion:** `curl -X POST /oauth/token grant_type=refresh_token` zweimal parallel. Beide bekommen Token-Pairs, Replay-Detection greift nicht.
**Impact:** Replay-Detection (Family-Revoke) bricht — Race-Window ermöglicht Doppel-Issue ohne Detection.
**Fix:** Conditional UPDATE: `UPDATE ... SET rotated_at = ? WHERE id = ? AND rotated_at IS NULL` und auf `meta.changes === 1` prüfen.

## #A-010 🟠 [Auth] Magic-Link User-Enumeration via Timing/DB-Side-Effect
**Datei:** [src/auth/magic-link.ts:46-53](src/auth/magic-link.ts:46)
**Beschreibung:** Bei vorhandenem Customer wird ein DB-Update + DB-Insert ausgeführt; bei fehlendem Customer nur ein SELECT. Antwort ist zwar identisch (`ok: true, ttl_sec`), aber die Latenz ist messbar verschieden.
**Impact:** Email-Enumeration via Timing-Side-Channel.
**Fix:** Entweder always-do-work (Fake-Inserts mit Wegwerf-Hash) oder einheitliche Latenz via `ctx.waitUntil` mit fixem Sleep.

## #A-011 🟡 [Auth] Magic-Link Race auf Code-Verify
**Datei:** [src/auth/magic-link.ts:92-113](src/auth/magic-link.ts:92)
**Beschreibung:** SELECT (token, attempts) → UPDATE (consumed_at). Zwei parallele `verify`-Requests mit gleichem Code könnten beide den Token finden und consumieren.
**Impact:** Doppel-Login (zwei Token-Paare) — niedrig, weil Customer trotzdem authentifiziert bleibt.
**Fix:** Conditional UPDATE auf `consumed_at IS NULL`.

## #A-012 🟡 [Auth] Magic-Link MAX_ATTEMPTS-Bypass via Re-Issue
**Datei:** [src/auth/magic-link.ts:55-72](src/auth/magic-link.ts:55), [src/auth/magic-link.ts:111](src/auth/magic-link.ts:111)
**Beschreibung:** Beim Request wird der vorherige Code consumed → attempts-Counter resetet auf neuem Token. Mit Rate-Limit 3/min Magic-Link-Request kann ein Attacker effektiv beliebig oft brute-forcen, indem er nach 4 Fehlversuchen einen neuen Code anfordert.
**Impact:** 32^8 ≈ 10^12 Combos sind aber unrealistisch zu brute-forcen — niedrig praktisch, schwächt Defense-in-Depth.
**Fix:** Per-Customer-Window-Counter (z.B. 30 Versuche/Stunde unabhängig vom Token).

## #A-013 🟡 [Auth] JWT-Secret pro Request aus D1 geladen (kein Cache)
**Datei:** [src/middleware/customer-auth.ts:36-41](src/middleware/customer-auth.ts:36), [src/routes/mcp.ts:44-47](src/routes/mcp.ts:44)
**Beschreibung:** Jeder Customer-authentifizierte Request macht D1-SELECT auf `tenants` zur Secret-Auflösung. Bekanntes Issue im Code-Kommentar erwähnt.
**Impact:** Latenz + D1-Cost; bei p99-SLO `auth.duration_ms < 200` wird das eng. Außerdem amplifiziert Login-Bursts den D1-Read-Druck.
**Fix:** KV-Cache `tenant_jwt_secret:<tenant_id>` mit 60s TTL + Invalidierung bei Rotate.

## #A-014 🟡 [Auth] HMAC-Skew-Toleranz 5min ohne Replay-Cache
**Datei:** [src/middleware/auth.ts:9, 33-34](src/middleware/auth.ts:9)
**Beschreibung:** ±300s Skew-Tolerance. Es gibt keine Nonce/Request-ID-Replay-Cache → ein abgefangenes signiertes Request kann 5min lang replayed werden.
**Impact:** MITM/Log-Leak → 5min Replay-Window. Bei TLS+CF-Edge praktisch eng.
**Fix:** KV-basierter Replay-Cache (Hash signature + timestamp, TTL=2×Skew). Bei Hit → 401.

## #A-015 🟡 [Auth] `client_id`-Vergleich nicht constant-time
**Datei:** [src/routes/auth.ts:148](src/routes/auth.ts:148)
**Beschreibung:** `if (row.client_id !== parsed.data.client_id)` — String-Equal mit short-circuit. client_id ist nicht geheim, aber Best-Practice.
**Fix:** `constantTimeEqualHex` oder einfach belassen — niedriges Risiko.

## #A-016 🟢 [Auth] `request_id`-Header blind übernommen
**Datei:** [src/middleware/request-id.ts:6-7](src/middleware/request-id.ts:6)
**Beschreibung:** Eingehender `X-Request-Id` wird ohne Validierung als interne Korrelation übernommen. Attacker kann beliebige Strings (inkl. Newlines) injizieren — relevant für Log-Aggregation.
**Impact:** Log-Injection / Log-Pollution.
**Fix:** Validierung `^[A-Z0-9_-]{8,80}$`, sonst neuen ULID erzeugen.

## #A-017 🟢 [Auth] `routes/auth.ts:21,46,65` etc. `c.req.json().catch(()=>({}))`
**Datei:** mehrere Stellen
**Beschreibung:** Konsistenter Fallback auf `{}` bei Parse-Fehler — gut. Aber andere Routen (`orders.ts:21`, `customers.ts:28`) haben kein `.catch` → Parse-Error → 500 statt 400.
**Fix:** Einheitliche Body-Parse-Helper-Funktion mit RFC-7807 400-Response.

## #A-018 🟢 [Auth] Resolve-Tenant-Slug öffnet Timing-Channel
**Datei:** [src/routes/auth.ts:33-41](src/routes/auth.ts:33)
**Beschreibung:** Existierender Slug → DB-Hit + Status-Check; nicht-existierender → DB-Hit, dann throw. Beide Pfade haben fast gleiche Latenz, aber bei großer Tenant-Tabelle können Index-Hits/Misses messbar differieren.
**Impact:** Tenant-Slug-Enumeration (low — Slugs sind eh nicht geheim).
**Fix:** Optional — pre-warm KV-Cache `tenant_slug:<slug>`.

## #A-019 ℹ️ [Auth] OAuth-Authorize konsumiert Magic-Link-Code, dann nochmal Token-Endpoint
**Datei:** [src/routes/auth.ts:101-117](src/routes/auth.ts:101)
**Beschreibung:** `verifyMagicLink` consumiert den Code; dann wird ein authorization_code ausgegeben. UX: User darf nicht zweimal `/authorize` mit gleichem Magic-Code aufrufen, bekommt sonst `GH-AUTH-006`. Doku-Hinweis nötig.

# 2. Multi-Tenancy & IDOR

## #T-001 🔴 [IDOR] `POST /v1/customer/devices` ohne Tenant-Filter beim Token-Lookup
**Datei:** [src/routes/devices.ts:32-36](src/routes/devices.ts:32)
**Beschreibung:** `db.select().from(devices).where(eq(devices.push_token, parsed.data.push_token))` — kein `tenant_id`-Filter. Customer aus Tenant A registriert push_token, dieser wird beim nächsten Request unter customer_id (Tenant B) reassigned.
**Reproduktion:** Customer A registriert push_token X. Customer B (anderer Tenant) registriert mit gleichem push_token X (OS-Level kann er den selben Token aus FCM bekommen, aber realistischer: Attacker wählt bekannten Token). Code in Zeile 34 macht `update.where(eq(devices.id, existing.id))` ohne Tenant-Check und überschreibt customer_id+tenant_id.
**Impact:** Cross-Tenant Push-Token-Hijack; Push-Notifications von Tenant A landen auf Customer von Tenant B.
**Fix:** `where(and(eq(devices.push_token, ...), eq(devices.tenant_id, tenant_id)))`. Bei existierendem Token aus anderem Tenant: insert neuen Eintrag, oder reject.

## #T-002 🟠 [IDOR] `DELETE /v1/customer/devices/:id` ohne Tenant-Filter
**Datei:** [src/routes/devices.ts:53](src/routes/devices.ts:53)
**Beschreibung:** Filter ist `eq(devices.id, id) AND eq(devices.customer_id, customer_id)` — kein `tenant_id`. Da customer_id ULID-scoped ist, sehr unwahrscheinlich aber bricht Defense-in-Depth.
**Fix:** `tenant_id` zur WHERE-Clause.

## #T-003 🟠 [IDOR] `services/invoice.ts findByOrderId` ohne tenant_id
**Datei:** [src/services/invoice.ts:24](src/services/invoice.ts:24), [Zeile 32](src/services/invoice.ts:32)
**Beschreibung:** `invoices.where(eq(invoices.order_id, opts.order_id))` und `customers.where(eq(customers.id, order.doc.customer_id))` — beide ohne `tenant_id`-Filter.
**Impact:** Falls ULIDs jemals kollidieren (~ Quasi-unmöglich) wäre Cross-Tenant-Read möglich. Defense-in-Depth.
**Fix:** Tenant-Filter überall (auch in Services), nicht nur in Repos.

## #T-004 🟠 [IDOR] `push.ts:39` Push-Send ohne tenant_id-Filter
**Datei:** [src/services/push.ts:39](src/services/push.ts:39), [Zeile 58](src/services/push.ts:58)
**Beschreibung:** `select.from(devices).where(eq(devices.customer_id, ...))` — wenn customer_id Cross-Tenant kollidieren würde, würde Push an falschen Tenant gehen. Auch `invalidateToken` ohne tenant_id.
**Fix:** Tenant_id zum Filter hinzufügen (params.tenant_id ist bereits vorhanden).

## #T-005 🔴 [SSRF] Webhook-URL ohne Validierung gegen private IP-Ranges
**Datei:** [src/routes/webhooks.ts:13-41](src/routes/webhooks.ts:13), [src/services/outbox.ts:87](src/services/outbox.ts:87)
**Beschreibung:** `z.string().url()` akzeptiert `http://localhost`, `http://10.0.0.1`, `http://169.254.169.254` (Cloud Metadata), CF-internal-only-domains. Outbox `fetch(sub.url)` würde sie ansprechen.
**Impact:** SSRF gegen CF-Edge: Customer kann seinen Tenant nutzen, um CF-Edge auf interne Services zu zwingen (Metadata-Endpoints, andere Tenant-Worker via internal hostnames). Wahrscheinlich blockt CF einige Bereiche, aber http://localhost könnte auf Worker-internal Routen treffen.
**Fix:**
- HTTPS-only erzwingen (`https://`).
- Hostname-Allowlist oder Block private/loopback ranges (`10.0.0.0/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`, `::1`, `fc00::/7`).
- Optional: Domain-Verifizierung (DNS-TXT-Token bei Webhook-Erstellung).

## #T-006 🔴 [Logic] R2-Key-Path durch User-kontrolliertes Content-Type
**Datei:** [src/routes/products.ts:140-148](src/routes/products.ts:140)
**Beschreibung:** `ext = ct.split("/")[1]?.split(";")[0]`. Content-Type `image/../../etc/passwd` passt `startsWith("image/")` Check, ext = `../../etc/passwd`. R2-Key wird `<tenant>/products/<id>/<hash>.../etc/passwd`.
**Impact:** R2 hat keine Verzeichnisse, also kein klassisches Path-Traversal. Aber: Object-Listing-Tools, Backup-Skripte und CDN-Caches können verwirrt werden; R2-Key kann auch fremde Buckets nicht verlassen.
**Fix:** `ext` gegen Whitelist: `if (!["png","jpeg","jpg","webp","gif","svg"].includes(ext.toLowerCase())) reject`.

## #T-007 🟡 [Info-Leak] Public OpenAPI + GIT_COMMIT in /health
**Datei:** [src/routes/health.ts:7-13](src/routes/health.ts:7), [src/openapi/index.ts:12](src/openapi/index.ts:12)
**Beschreibung:** `/health` exposiert `WORKER_VERSION` + `GIT_COMMIT` (Recon: Attacker mappt Commit-Hash auf bekannte CVEs). `/openapi.json` ist public ohne Auth.
**Impact:** Niedrig; Mapping auf Vulnerabilities möglich.
**Fix:** GIT_COMMIT auf Production nicht setzen oder hashen. OpenAPI nur in non-prod public; in prod tenant-authentifiziert.

## #T-008 🟡 [IDOR] Cursor (base64 JSON) nicht signiert
**Datei:** [src/routes/orders.ts:154-158](src/routes/orders.ts:154), [src/routes/customers.ts:115-122](src/routes/customers.ts:115), [src/routes/products.ts:74-78](src/routes/products.ts:74)
**Beschreibung:** Cursor ist `btoa(JSON.stringify({created_at, id}))`. User kann beliebige `created_at` injizieren. Repo filtert dann mit `lt(orders.created_at, params.cursor.created_at)` — aber `tenant_id`-Filter ist immer dabei, also kein IDOR möglich.
**Impact:** Niedrig. Cursor-Tampering ändert nur Pagination-Window.
**Fix:** Optional: HMAC-signierte Cursor mit Tenant-bound Secret.

## #T-009 🟡 [Tenant] dsgvo.ts UPDATE ohne tenant_id in WHERE
**Datei:** [src/services/dsgvo.ts:90](src/services/dsgvo.ts:90)
**Beschreibung:** Vorher SELECT mit Tenant-Check, dann UPDATE nur auf `eq(customers.id, opts.customer_id)`. Defense-in-Depth-Gap.
**Fix:** `where(and(eq(customers.id, ...), eq(customers.tenant_id, opts.tenant_id)))`.

## #T-010 🟠 [Tenant] `invoice.ts:30` Tenant ohne deleted_at-Check
**Datei:** [src/services/invoice.ts:30](src/services/invoice.ts:30)
**Beschreibung:** `tenants.where(eq(tenants.id, opts.tenant_id))` — kein `isNull(tenants.deleted_at)`. Wenn Tenant soft-deleted, würde Invoice trotzdem generiert.
**Fix:** `isNull(tenants.deleted_at)` ergänzen.

## #T-011 🟠 [Logic] `mcp.ts list_orders`-Tool ohne customer-self-Filter
**Datei:** [src/routes/mcp.ts:227-233](src/routes/mcp.ts:227)
**Beschreibung:** `list_orders` filtert via `customer_id: auth.customer_id` — also customer_self. Aber `input.state` ist `z.string().optional()` ohne Enum-Constraint; jeder String akzeptiert.
**Impact:** SQL-Filter mit beliebigem state — kein Sicherheitsbug, aber inkonsistente API.
**Fix:** `state: OrderStateSchema.optional()` im Tool-Inputschema.

# 3. Input-Validation & Schemas

## #V-001 🟠 [Schema] Keine `.strict()` auf Customer/Product/Order-Schemas
**Datei:** [src/schemas/customer.ts:14-29](src/schemas/customer.ts:14), [src/schemas/product.ts:12-23](src/schemas/product.ts:12), [src/schemas/order.ts:99-125](src/schemas/order.ts:99)
**Beschreibung:** Zod default = unbekannte Felder werden silentlich gestrippt. Für Mutating-APIs Best-Practice ist `.strict()` → 400 bei Unknown.
**Impact:** Verwirrte Clients schicken Tippfehler (`emai` statt `email`) → silent ignored, Customer hat keine Email gesetzt aber bekommt 201.
**Fix:** `.strict()` auf alle Create/Patch-Schemas.

## #V-002 🟠 [Schema] `metadata`/`source`/`actor`/`audit` als `z.record(z.unknown())`
**Datei:** [src/schemas/customer.ts:28](src/schemas/customer.ts:28), [src/schemas/order.ts:108-110, 121, 123-124](src/schemas/order.ts:108)
**Beschreibung:** Beliebige JSON-Inhalte erlaubt — DB-Größe/CPU bei rekursiver JSON-Tiefe.
**Impact:** DoS via tief verschachtelter `metadata` (z.B. `{"a":{"a":...}}` 10000 deep) → JSON.parse stack overflow oder D1-Storage-Bloat.
**Fix:** Größenlimit (`z.record(z.unknown()).refine((v) => JSON.stringify(v).length < 16384)`), Tiefenlimit-Refine, oder eng-typisierte Felder.

# 5. Money / Decimal / Pricing

## #M-001 🟠 [Money] Banker's Rounding `roundHalfToEven` unvollständig für negative Werte
**Datei:** [src/engines/pricing.ts:97-103](src/engines/pricing.ts:97)
**Beschreibung:** `Math.floor(-1.5) = -2`, `diff = -1.5 - -2 = 0.5`. Branch `diff === 0.5` (eigentlich nicht erreicht wegen Float, aber bei `0.5` exakt): `floor%2 === 0 ? -2 : -1` → `-2`. **Korrekt** für `-1.5`. Aber: Float-Ungenauigkeit: `0.1 + 0.2 = 0.30000000000000004`, daher `diff > 0.5` Branch wird bei `0.5000000001` getriggert → `floor + 1`. Banker's-Rounding ist ein Hack, nicht echt.
**Impact:** Ein-Cent-Drift bei %-Rabatten unter Float-Ungenauigkeit. Kann sich kumulieren.
**Fix:** Decimal-Library (mikrocent / Big.js / dnum) oder Integer-Cent × 10000 Mikro-Cent + Roundtrip am Ende.

# 6. Stock / FEFO / Race Conditions

## #S-001 🔴 [Race] `InvoiceNumberDO./next` nicht-atomisch read-modify-write
**Datei:** [src/do/invoice-number.ts:18-30](src/do/invoice-number.ts:18)
**Beschreibung:** `state = await this.loadOrInit()` → modify → `await this.ctx.storage.put`. Cloudflare Durable Objects serialisieren standardmäßig nur via Input-Gates, aber wenn der fetch-Handler `await` macht ohne Storage-Call, könnten verschachtelt zwei Events laufen. Außerdem: kein `blockConcurrencyWhile`.
**Reproduktion:** Zwei parallele `/next`-Requests; beide laden state.next_number=42; beide schreiben 43. Beide bekommen Nummer 42 → Duplikat-Rechnungsnummer.
**Impact:** Buchhaltungs-Compliance: Rechnungen müssen lückenlos UND eindeutig sein. Duplikate = §14 UStG / §147 AO Verstoß.
**Fix:** `await this.ctx.blockConcurrencyWhile(async () => { ... })` um den ganzen `/next`-Block. Oder DB-`uniq_invoice_number` (existiert bereits) → Insert-Conflict-Retry.
**Verifikation:** uniq-Index `idx_invoices.uniq_invoice_number` würde Duplikate auf D1-Ebene catchen, aber DO würde dennoch zwei verschiedene Rechnungs-Records mit gleicher Nummer ausgeben — der zweite Insert wirft. Der Caller sieht 500.

**Fix:** `blockConcurrencyWhile` um die Body-Read+State-Mutation oder explicit `state.storage.transaction`.

## #S-003 🟠 [Race] `CronLockDO./acquire` nicht-atomar
**Datei:** [src/cron/lock-do.ts:19-29](src/cron/lock-do.ts:19)

# 7. Idempotency & Rate-Limit

## #I-001 🔴 [Idempotency] In-Flight Race auf gleichem Idempotency-Key
**Datei:** [src/middleware/idempotency.ts:23-54](src/middleware/idempotency.ts:23)
**Beschreibung:** Zwei parallele Requests mit gleichem Key: beide `KV.get → null`, beide rufen Handler, beide schreiben in DB → **doppelte Order/Customer/etc. trotz Idempotency-Key**. Cache wird erst nach next() geschrieben.
**Reproduktion:** `parallel curl -X POST /v1/orders -H "X-Idempotency-Key: K1" ...` — beide Requests landen am Order-Repo, beide insertieren.
**Impact:** Doppel-Buchung — Idempotency-Garantie verletzt; klassisches Issue.
**Fix:** "PUT-if-absent" via KV (KV hat keine compare-and-swap, daher müsste das per Durable-Object oder D1-Lock-Tabelle gemacht werden). Alternativ: D1-Insert mit `idempotency_key` UNIQUE-Constraint pro Tenant (Idempotency-Tabelle mit dem Key + result-row); zweiter Insert würde uniq-Conflict werfen, dann KV-Read.

## #I-002 🟠 [Idempotency] Fail-Open bei KV-Down
**Datei:** [src/middleware/idempotency.ts:35-39](src/middleware/idempotency.ts:35)
**Beschreibung:** KV-get wirft → durchlassen mit Warning-Header.
**Impact:** Bei KV-Outage Doppel-Buchungen.
**Fix:** Tenant-Setting `idempotency_strict_mode = on` → fail-closed; oder DO-Backed Strict-Variante.

## #I-003 🟠 [Idempotency] Cached Response verliert Headers
**Datei:** [src/middleware/idempotency.ts:46-53](src/middleware/idempotency.ts:46)
**Beschreibung:** Reply enthält nur Content-Type + X-Idempotency-Hit + X-Request-Id. Andere Headers (z.B. `Location`, `ETag`, eigene Custom) werden nicht zurückgespielt.
**Impact:** Original-Response (z.B. `Location: /v1/orders/ord_abc`) beim Replay weg → Client-Verwirrung.
**Fix:** Headers-Set in CacheEntry persistieren.

## #I-004 🟠 [Idempotency] Body-Hash über Raw-Body sensitiv auf Whitespace/Reihenfolge
**Datei:** [src/middleware/idempotency.ts:30-31](src/middleware/idempotency.ts:30)
**Beschreibung:** `payloadHash = sha256(method+path+body)`. Wenn Client JSON-keys in unterschiedlicher Reihenfolge serialisiert (oder mit/ohne Whitespace), bekommt er 409 statt Cache-Hit.
**Impact:** UX-Bug — Client-Retries die durch Lib-Update neue JSON-Reihenfolge haben → 409 statt Idempotency-Hit.
**Fix:** Canonical-JSON (sortierte Keys) für Hash, oder hash über parsed body.

## #I-005 🟠 [Rate-Limit] KV-Path eventual-consistency erlaubt Burst
**Datei:** [src/middleware/rate-limit.ts:86-112](src/middleware/rate-limit.ts:86)
**Beschreibung:** Non-strict-Klassen (`read_hot`, `write_critical` etc.) sind KV-only. KV-eventual-consistency erlaubt mehrere Workers gleichzeitig `count=N` zu lesen und `count=N+1` zu schreiben — keiner sieht den anderen.
**Impact:** `write_critical: 20/min` kann unter starker Last 50-100/min werden.
**Fix:** Alle Klassen DO-backed; oder akzeptieren als "loose" Hint.

## #I-006 🟠 [Rate-Limit] DoS-Bypass via KV-Storm
**Datei:** [src/middleware/rate-limit.ts:91-94](src/middleware/rate-limit.ts:91)
**Beschreibung:** KV-get-fail → fail-open. Attacker kann KV mit Garbage-Keys spammen, bis CF-Tier-Limits Failures triggern → Rate-Limit fällt aus.
**Impact:** Theoretisch — Cloudflare kappt KV-Spam wahrscheinlich vorher.
**Fix:** Fail-closed (`return 503 GH-RATE-001`) oder DO-Fallback ohne KV.

## #I-007 🟡 [Rate-Limit] Pre-Auth-Identifier kollabiert hinter NAT
**Datei:** [src/middleware/rate-limit.ts:115-120](src/middleware/rate-limit.ts:115)
**Beschreibung:** Default-Identifier `_anon_t/_anon_c/<ip>` für nicht-authentifizierte Endpoints. Hinter Corporate-NAT teilen viele User dieselbe IP → ein User kann den Bucket erschöpfen und alle anderen bekommen 429.
**Impact:** Auth-Login-Limit (5/min) wird für Corporate-Networks unbenutzbar.
**Fix:** Identifier mit Browser-Fingerprint-Hint (User-Agent + Accept-Language) als Tiebreaker; oder striktere Auth-Endpoints + lockerere Pre-Auth.

## #I-008 🟡 [Idempotency] Body wird nochmal gelesen via clone()
**Datei:** [src/middleware/idempotency.ts:30](src/middleware/idempotency.ts:30), [src/middleware/auth.ts:74](src/middleware/auth.ts:74)

## #P-001 🟠 [PDF] Helvetica-StandardFonts crash bei non-WinAnsi-Zeichen
**Datei:** [src/services/invoice-pdf.ts:79, 91, 107, 109, 156, 159, 162, 166](src/services/invoice-pdf.ts:79)
**Beschreibung:** pdf-lib StandardFonts.Helvetica nutzt WinAnsi-Encoding. User-controllable Strings (`tenant.name`, `customer.name`, `notes`) können €, Emoji, Kyrillisch, Chinesisch, Hebräisch enthalten — pdf-lib wirft `Cannot encode character`.

## #P-005 🟡 [Invoices] Direkt-R2-Stream durch Worker (kein Signed URL)

## #P-006 🟡 [VIES] Pfad-Variable nicht URL-encoded
**Datei:** [src/services/vies.ts:39-43](src/services/vies.ts:39)
**Beschreibung:** `https://ec.europa.eu/.../ms/${country}/vat/${number}`. `country` matched `[A-Z]{2}` (safe), aber `number` matched `.+` — kann `/`, `..`, etc. enthalten. Theoretisch Path-Traversal-Probe gegen EU-Service.
**Impact:** Niedrig (EU-Service ist read-only, Path-Traversal trifft nur auf andere Endpoints).
**Fix:** `encodeURIComponent(number)`. Oder strikter: `^[0-9A-Z]{2,12}$`.

## #P-007 🔴 [DSGVO] Pseudonymisierung greift nicht in R2-Backup-Inhalte
**Datei:** [src/services/dsgvo.ts:40-93](src/services/dsgvo.ts:40), [src/services/backup.ts:9-24](src/services/backup.ts:9)
**Beschreibung:** Pseudonymize-Customer ersetzt PII in `customers`-Tabelle. Backup-R2 enthält Snapshots VOR der Pseudonymisierung — DSGVO Art. 17 verlangt Löschung "auch in Backups, soweit machbar".
**Impact:** Compliance-Lücke. Behörden-Anfrage: Customer X hat Recht auf Vergessenwerden ausgeübt — Backup vom Vortag enthält noch alle PII.
**Fix:** Backup-Retention auf 30d kappen (regulatorisch akzeptabler Kompromiss); ODER Backup-Re-Encryption mit pro-Customer-Key, der bei Pseudonymize zerstört wird (Crypto-Shredding).

## #P-008 🟠 [DSGVO] Order/Invoice-PII nicht pseudonymisiert
**Datei:** [src/services/dsgvo.ts](src/services/dsgvo.ts), [src/db/schema/orders.ts:14-19](src/db/schema/orders.ts:14)
**Beschreibung:** `customer_snapshot` in `orders` enthält Name/VAT-ID/Country. Diese werden bei Pseudonymize NICHT angefasst (10y-Retention für Orders).
**Impact:** PII verbleibt in Orders → de-facto kein Recht auf Vergessen für Bestelldaten. Das ist juristisch verteidbar (§147 AO), aber sollte explizit dokumentiert sein.
**Fix:** Doku: "Order-Snapshots bleiben für 10 Jahre. Pseudonymize ersetzt nur Customer-Master." + Audit-Log auf Order-Ebene.

## #P-009 🟠 [DSGVO] Kein Right-to-Export-Endpoint
**Datei:** [src/routes/dsgvo.ts](src/routes/dsgvo.ts)
**Beschreibung:** Nur `pseudonymize-customer`. DSGVO Art. 15 (Auskunftsrecht) und Art. 20 (Datenübertragbarkeit) brauchen Export.
**Impact:** Compliance-Lücke.
**Fix:** `POST /v1/dsgvo/export-customer` → JSON-Bundle mit Customer + Orders + Invoices.

## #P-010 🟠 [DSGVO] Pseudonymize-Endpoint ohne Rate-Limit
**Datei:** [src/routes/dsgvo.ts:15](src/routes/dsgvo.ts:15)
**Beschreibung:** Mounted unter `v1` mit `auth+idempotency`, aber kein eigener `rateLimit({class:"write_critical"})`.

## #M-001 🔴 [MCP] Scope-Check-Logik invertiert/verwirrt
**Datei:** [src/routes/mcp.ts:99](src/routes/mcp.ts:99)
**Beschreibung:** `if (tool.scope === "write" && !auth.scopes.includes("customer_self"))` — Lesen: write-Tool ist erlaubt wenn `customer_self` im Scope ist. `customer_self` ist aber der DEFAULT-Scope für jeden eingeloggten Customer. → **Jeder authentifizierte Customer kann ALLE write-Tools aufrufen.**
**Reproduktion:** Customer-JWT (scope=`["customer_self"]`) → call MCP `confirm_order` → erlaubt; call `cancel_order` → erlaubt.
**Impact:** Kein Privilege-Separation. Das ist im v1 ggf. **gewollt** (Customer darf seine eigenen Orders confirmen), aber das Scope-Check-Pattern ist trügerisch — bei Erweiterung um Tenant-MCP-Tools (z.B. `pseudonymize_customer`) wird das gefährlich.
**Fix:** Scope-Naming: `customer_read`, `customer_write` separat. Tool.scope auf required-Scope-String mappen, nicht read/write-binary.

## #M-002 🟠 [MCP] `zodToJsonSchema` unvollständig — Enums/Unions/Literals fallback `string`
**Datei:** [src/routes/mcp.ts:239-257](src/routes/mcp.ts:239)
**Beschreibung:** ZodEnum, ZodUnion, ZodLiteral, ZodNullable etc. werden nicht behandelt → `{type:"string"}`.

## #M-003 🟡 [MCP] /initialize ohne Auth exposiert serverInfo
**Datei:** [src/routes/mcp.ts:67-72](src/routes/mcp.ts:67)
**Beschreibung:** Standard MCP-Pattern, aber `serverInfo.version` exposed → Recon.
**Impact:** Niedrig.

## #M-004 🟠 [MCP] Prompt-Injection via Customer-Daten in Tool-Output
**Datei:** [src/routes/mcp.ts:178, 199, 217](src/routes/mcp.ts:178)
**Beschreibung:** `summary` enthält `${result.doc.totals.total_cents}`-Inline-Daten und Order-IDs. Wenn Customer-Name oder Notes maliziösen Text enthält ("Ignore previous instructions and..."), landet das im Model-Context.

## #L-002 🟠 [Info-Leak] Generischer Error-Pfad inkludiert `err.message` als `cause`
**Datei:** [src/errors/problem-json.ts:43-50](src/errors/problem-json.ts:43)
**Beschreibung:** Bei nicht-CodedError wird `err.message` in `cause` der Problem-JSON-Antwort gepackt. SQL-Errors, JSON-Parse-Errors etc. enthalten stack-Hints, Tabellennamen, etc.
**Reproduktion:** Send malformed JSON → `JSON.parse` throws SyntaxError → message "Unexpected token..." landet im 500-Body.
**Impact:** Info-Leak (Stack-Trace-Light, internal-Names).
**Fix:** In Production `cause` weglassen oder konstant "internal_error".

## #L-003 🟠 [Headers] Keine Security-Headers (HSTS, CSP, X-Frame-Options, X-Content-Type-Options)
**Datei:** [src/index.ts:21-89](src/index.ts:21), keine `securityHeaders()`-Middleware
**Beschreibung:** Hono setzt von sich aus keine Security-Headers. CF-Edge fügt einige hinzu, aber HSTS/CSP/X-Frame-Options/Referrer-Policy/Permissions-Policy sind nicht garantiert.
**Impact:** Wenn Frontend HTML serviert (nicht der Fall hier — JSON-API), trotzdem Best-Practice. Auch für /openapi.json wäre `X-Content-Type-Options: nosniff` gut.
**Fix:** Globale Middleware:
```ts
app.use("*", async (c, next) => { await next();
  c.res.headers.set("Strict-Transport-Security", "max-age=31536000; includeSubDomains");
  c.res.headers.set("X-Content-Type-Options", "nosniff");
  c.res.headers.set("Referrer-Policy", "no-referrer");
});
```
